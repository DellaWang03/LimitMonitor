# 交易前试算 MVP：数据库上下文设计

状态：待用户复核。用户复核通过后，本设计将替代 `PRETRADE_SHARED_CORE_SPEC.md` 中关于“全量不可变闭包、34 张兼容投影、类型化事实表、Wind 落库和独立 TEST 账号”的首版要求。

基线：GitHub `main@579af695fb8727dec8249f66d07a8b0e723da137`，以及已通过零差异验收的共同内核候选 `970ef6daa82dfb9fa4e458dd1da30f496ab26447`。

## 1. 目标与范围

本阶段只为两个新增交易前功能建立最小、可验证的数据上下文：

1. 给定债券和拟买入账户，计算交易前 PR 可购剩余额度；
2. 给定一揽子债券、拟买金额和账户，计算交易后是否超限。

交易前服务必须调用 `ProductionRiskKernel`，不能从现有展示结果表拼装新的限额规则。每日 Stage1/Stage2 与交易前功能继续共用同一生产业务内核。

本阶段不改既有页面、既有 `ArchiveDB`、`archive_meta`、16 张上线归档表或其 `is_current` 指针。新代码只创建并写入 `pretrade_` 前缀的新表。

## 2. 已确认的业务和运行决定

- 最新完整的限额上下文由交易前模块自己的 `PROD` current 指针选择；不设置 T-1 新鲜度硬门槛。
- 交易前计算使用数据库中的持仓、限额、配置、池、评级、分类和分母；不得读取 `data/current`、本地 Excel 或旧展示结果作为计算输入。
- 非持仓债所缺的债券主数据允许当次按需调用 Wind，使用最新可用返回；Wind 数据不落库、不建缓存表、不要求与限额快照同日。
- Wind 返回先在内存中标准化为生产规范记录，再和数据库上下文一起进入同一共同内核。缺少必需字段时结果为不可计算，并披露缺失原因；不得补零、默认归类或把缺失解释为不适用。
- `issuer_wind_code_mapping.csv` 是已确认可复用的静态解析依赖，不另建历史数据库表；本次运行只记录其 SHA-256、行数和验证时间。
- 开发和验收使用现有阿里云正式数据库，但只写交易前模块的 `DEV` 上下文；不增加独立 TEST 账号或 schema。线上交易前页面只读取 `PROD` 指针。

## 3. 为什么只持久化共同内核输入

当前上线数据库归档的是 4 张 Stage0 输入表和 12 张展示结果表。展示结果能够支撑现有看板，但不是新增交易前功能的生产输入：它们无法可靠地为非持仓债重建主体、实控人、担保、地域、高风险、高收益和限额覆盖关系。

`ProductionRiskKernel` 的外部输入为 27 张唯一 DataFrame、业务日期和监管集中度参数。Stage2 的两张 Stage1 交接表由内核重新计算，不属于外部输入。首版只持久化这 27 张输入和参数；内核输出不额外作为数据库业务表保存。

其中 4 张（债券池、主体池、调整实控人、净资产）已在旧归档中存在。为避免 `DEV` 验收把 `data_source_0123` 与线上旧表拼接，`pretrade_` 上下文仍保存完整 27 张输入。此处的 4 份重复仅是小型、同批次的运行副本，不引入新的业务数据或第二套限额逻辑。

### 3.1 27 张固定输入

| 类别 | 数据集 |
|---|---|
| 持仓 | 债券持仓明细表、债券持仓明细表_信用债、债券持仓明细表_全量债券监管集中度、债券持仓表_核算系统 |
| Stage0 / 池与调整 | 风控部债券池、风控部主体池、调整实控人名单、公司净资产_手工_每日 |
| 参考与映射 | 穿透高收益债券、金融工具池设置、中债隐含评级AAA&AAA+、发行人类型调整表、ISIN码映射 |
| Stage1 限额配置 | 单一债券集中度限额、单一债券规模限额、特批单一债券限额、单一主体规模限额、单一实控人规模限额、特定主体限额、特定实控人限额、单一担保公司规模限额 |
| Stage2 配置与历史 | 高风险行业、高风险省份、高风险限额、地域集中度限额(含城投)、穿透高收益_投资本金规模、高收益限额 |

这个清单是唯一输入注册表；实现不得手工从展示表补字段，也不得按查询场景选择性漏存输入。

## 4. 最小数据库结构

所有表位于现有阿里云数据库，表名固定为 `pretrade_` 前缀。迁移只允许创建这四张表和必要索引；不得自动修改旧表结构。

### 4.1 `pretrade_snapshot`

一行代表一次完整的交易前上下文构建。

必填字段：

- `snapshot_id`：UUID 主键；同一 `data_date` 重跑也必须创建新 ID；
- `usage`：`DEV` 或 `PROD`；
- `data_date`：共同内核业务日期；
- `status`：`LOADING` 或 `READY`；
- `code_commit`、`engine_version`、`input_contract_version`；
- `source_manifest_hash`：本次运行实际消费的文件、sheet、日期策略和静态映射摘要的哈希；
- `input_hash`：27 张输入和参数的汇总哈希；
- `regulatory_concentration_limit`、`created_at`、`ready_at`、`note`。

`READY` 快照不得被更新。首版不保存 `VALIDATED`、`FAILED`、父快照或发布审计流水：构建任一步失败均回滚事务，不留下可读快照。

### 4.2 `pretrade_snapshot_dataset`

每个 `(snapshot_id, dataset_code)` 一行，恰好对应上述 27 个数据集。字段至少包括：

- `dataset_code`、`ordinal`、`row_count`；
- `serializer_version`、`schema_json`、`content_hash`；
- `source_meta_json`：实际来源文件/Sheet 或 Stage0/Stage1 运行来源、允许空表标识；
- `payload_size_bytes`。

数据集内容使用版本化 Parquet 序列化；读取端必须按保存的列顺序和逻辑类型恢复 DataFrame。任一输入不能被该序列化器无损往返时，归档直接失败，不允许静默退化到字符串或 pickle。

### 4.3 `pretrade_snapshot_dataset_chunk`

Parquet 压缩后的二进制按固定顺序拆分为不超过 8 MiB 的块，避免 MySQL `max_allowed_packet` 限制。主键为 `(snapshot_id, dataset_code, chunk_ordinal)`，内容列为二进制数据。读取时必须按 `chunk_ordinal` 完整拼接，并校验 `content_hash` 后才允许反序列化。

分块是为已知大持仓输入准备的传输约束，不表示引入逐行血缘、对象存储或数据湖。

### 4.4 `pretrade_snapshot_current`

每个 `usage` 仅一行，保存 `snapshot_id`、`switched_at`。它只服务交易前模块，不关联也不修改 `archive_meta.is_current`。

- `DEV` 验收可显式切换 `DEV` 指针；
- `PROD` 指针只能指向同为 `PROD` 且 `READY` 的快照；
- `PROD` 发布使用独立显式命令；构建或测试命令默认且强制使用 `DEV`，不自动发布。

## 5. 写入、读取与计算流程

### 5.1 每日上下文构建

1. 每日生产运行从真实适配器加载数据，并在构造 `ProductionKernelInput` 时冻结 27 张实际内存输入、业务日期和参数；不得在计算结束后重新打开“当前 Excel”。
2. 归档器启动一个数据库事务，插入 `LOADING` 快照、27 条 dataset 元数据和全部 payload 块。
3. 在事务内从刚写入的数据重建 27 张输入，校验数据集哈希、汇总输入哈希和 Parquet 往返一致性。
4. 校验通过后把快照置为 `READY` 并提交；任一失败回滚，旧 `DEV`/`PROD` current 均不变化。
5. 构建与发布分离。只有显式发布操作才在一个短事务内切换相同 `usage` 的 `pretrade_snapshot_current` 指针。

首版不运行正式旧归档脚本作为 `data_source_0123` 验收入口，也不调用 `ArchiveDB.write_batch()`；后者按 `data_date` 删除重写并切换全站 `archive_meta`，会影响已上线页面。

### 5.2 交易前读取

1. 页面或服务按用途解析 `pretrade_snapshot_current`；开发工具允许显式 `snapshot_id`，线上只允许 `PROD` current。
2. 读取器只加载同一 `READY` 快照的 27 个 dataset，校验哈希并恢复 `ProductionKernelInput`。
3. 交易前适配器校验账户：账户必须来自该快照完整持仓输入中已归档的允许账户集合；未知账户必须拒绝，不能静默进入基线的自营 `else` 分支。
4. 对持仓债，从数据库输入中取得生产规范主数据；对非持仓债，调用 Wind、标准化本次内存记录并进行字段完整性校验。
5. 单券和一揽子交易分别将拟买增量送入相同 `ProductionRiskKernel`；两者不得从旧展示表、未经标准化和完整性校验的 Wind 原始返回，或第二套公式计算剩余额度。

Wind 返回是本次查询的唯一非数据库业务输入。它不落库、不会改变 current，也不会被后续查询隐式复用。

## 6. 错误处理与数据质量

- 27 个输入中缺少任一必需键、哈希不符、序列化失败、反序列化失败或业务日期不一致：快照构建失败并回滚。
- `READY` 以外的快照不可读取；读取到不完整 dataset 或内容哈希不符时，服务失败关闭。
- Wind 缺少必需主数据、池或限额输入缺失、未知账户、非法金额、缺少高收益全价成本等情况，沿用权威规格的数据质量层，返回不可计算及原因；不得改变生产业务字段。
- 明确的零持仓、零限额和不适用必须继续与缺失区分；不得将 `0`、空值和不适用互相替代。

## 7. 验收范围

以 `/Users/dellawang/Desktop/LimitMonitorAutomation/data_source_0123` 的冻结 manifest 为唯一首轮验收输入。

必须通过：

1. 27 个输入分别完成 Parquet 序列化、数据库分块写入、读取和恢复；列顺序、逻辑类型、日期、Decimal/数值、空值、行数和内容哈希均一致。
2. 从 `DEV` 快照数据库读回的输入重跑共同内核，Stage1 35 张和 Stage2 22 张结果与冻结金样逐表、逐行、逐字段零差异。
3. 同一 `data_date` 两次构建产生不同 `snapshot_id`，并都可以显式读取和重放。
4. 注入任一 dataset 写入、块写入、哈希校验或反序列化失败时，事务回滚，`pretrade_snapshot_current` 不变化。
5. `DEV` 快照不得发布到 `PROD` 指针；构建命令不得对 `archive_meta`、既有16张归档表或既有页面读路径执行 DML。
6. 读取器在禁用文件 I/O 和网络 I/O 的测试中，仍能由数据库输入成功重建共同内核上下文。
7. 持仓债的单券试算与同债同账户单行篮子试算结果一致；一揽子按共享维度合并，拆行、合行和输入行顺序变化不得改变汇总结果。
8. 使用固定 Wind 响应夹具验证非持仓债：当次读取 Wind、标准化并进入共同内核成功；Wind 缺字段时返回不可计算，且没有任何 Wind 数据 DML。
