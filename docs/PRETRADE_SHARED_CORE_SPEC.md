## 1. 目标

新增以下两个交易前功能：

1. 给定一只债券和拟买入账户，返回交易前 PR 可购剩余额度；
2. 给定一揽子债券、拟买金额和拟买入账户，返回整篮交易后是否超限。

单券对高收益债券另行返回年度预计结算全价成本剩余；该值与 PR 可购额度是不同计量口径，不参与 PR 额度最小值。

两个功能必须与上线 Stage0、Stage1、Stage2 的限额口径保持一致。唯一允许不同的是债券主数据的取得方式：

- 持仓债主数据来自指定的不可变数据库快照；
- 非持仓债缺失的主数据来自 Wind；
- 两种来源都必须转换成同一份生产规范记录；
- 规范记录生成后的分类、关联、适用性、聚合、限额选择、公式、边界和状态判断必须调用同一个生产业务内核。

不得为交易前功能再实现一套平行的限额规则。

## 2. 权威来源和优先级

业务证据按以下顺序解释：

1. GitHub `main` 提交 `579af695...` 中的上线 Stage0、Stage1、Stage2 行为；
2. 该次运行实际使用的配置、参考表和输入数据；
3. 自动化特征测试和冻结金样；
4. 交易前页面、既有交易前测试和历史开发文档。

低优先级材料不得反向修改高优先级口径。历史交易前测试只能证明当前实现自洽，不能证明其业务正确。

### 2.1 生产金样的静态主体代码解析依赖

上线 Stage0 的 `issuer_wind_code_mapping.csv` 是主体名称到 Wind 主体代码的静态标识解析数据，不是按业务日期变化的持仓、池状态、占用、限额、分母或分类事实。因此，生产金样复算可以直接只读使用当前已确认稳定的映射，不要求其文件时间等于金样业务日，也不需要另建一张历史映射表，但必须同时满足：

- 不混入12个业务日输入文件；每次运行记录当前源文件的大小、SHA-256及验证时间；
- 校验主体名称唯一性和同名代码冲突，禁止运行时静默改写来源文件；
- 原文件保持只读；仅允许向本次隔离输出目录复制一份运行副本，生产 `data/current` 和归档保持不变；
- `To_WindCode` 明确返回的 `0` 按 `579af695...` 的会话结果语义保留，但不得伪造为可长期缓存的非零主体代码；
- 对长期映射未缓存的显式 `0`，可以只读当前 Stage0 主体输出、仅提取“发行人名称/发行人wind代码=0”，在隔离临时目录生成一次性会话结果；不得读取或复用其中的日期、主体池等业务字段；
- 该依赖只能完成主体代码解析，不得提供或覆盖池状态、限额分类、占用、限额值、分母及任何业务判断。

金样证据必须单独披露当前映射和零结果来源的哈希、行数及零结果主体清单。两个源文件变化时必须重新生成金样并做差分，但其文件时间晚于金样业务日本身不构成失败。

部署基线 `LimitDetailCalculator` 内部新建的 `ConfigLoader()` 仍会读取项目根下 `data_source_0123/限额配置_当前.xlsx`。隔离工作树复算时允许在该被 Git 忽略的部署兼容路径临时复制冻结清单中的同一文件；进入沙箱前后必须校验 SHA-256，子进程只能读取，退出后只删除由本次运行创建且内容未变化的文件和空目录。该兼容入口不得替换文件内容、改变限额值或修改 Stage1 代码。

本轮只做等价重构和新增功能接入，不包含任何业务规则升级。Stage0、Stage1、Stage2 的生产业务结果必须与 `579af695...` 零差异；此前讨论的关注池等建议不进入本轮。

本轮投产完成后的任何业务口径变化，必须另立项目并：

1. 修改共同业务内核；
2. 同时影响每日生产计算和交易前试算；
3. 记录新的规则版本、生效日期及业务决定；
4. 生成变更前后差分报告；
5. 使用新的冻结金样重新验收；
6. 禁止以交易前专用分支、回退值或白名单静默实施。

## 3. 不可变业务原则

### 3.1 共同内核

每日 Stage0/Stage1/Stage2 与交易前试算必须共用以下转换与计算能力：

- 债券代码标准化和单债归并键；
- 高收益识别；
- 中债隐含评级关联；
- 债券池、主体池、担保池关联；
- 发行人类型调整；
- 实际控制人调整、回退及占位值处理；
- 担保准入和担保适用性；
- 行业、省份、地域、城投和高风险标记；
- 1_1 / 1_2 路由；
- 特定主体、特定实控人和西咸例外；
- 单债、主体、实控人、担保人及 Stage2 共享风险范围；
- 对上线结果中已经存在的同一主体多约束进行无损保留；
- 同一实控人最终限额取值；
- 监管、地域、高风险和高收益公式；
- 剩余额度及超限判断。

交易前模块只负责：

- 接收交易输入；
- 选择数据库快照；
- 对持仓债从交易前数据库快照取得规范原始记录；对非持仓债当次调用 Wind、在内存中规范化并完成字段完整性校验；
- 把拟买交易转换为共同内核需要的规范增量；
- 调用共同内核；
- 将结构化结果展示或导出。

交易输入必须在进入共同内核前完成非业务性校验：账户必须来自已归档的允许账户清单并复用基线业务分类映射；未知账户不得利用基线 `else` 分支静默归为自营。用户拟买 PR 金额必须是有限正数；仅内部零增量特征测试允许使用 `0`。

债券池、主体池等成员关系只有在对应数据集完整、代码可标准化且精确无匹配时，才可以解释为“未入池”；否则记录数据质量缺失，不得推断为非成员。

### 3.2 特批单债

- `规模指标值` 生效；
- `集中度指标值` 在当前上线规则中不生效；
- 不得把未生效的特批集中度作为交易前额外约束。

### 3.3 1_1 / 1_2 与覆盖关系

交易前结果必须保留生产内核计算出的路由、覆盖来源和共享范围，不得根据最终展示表重新推断。首版至少用特征测试冻结以下 `579af695...` 行为：

- 普通信用债进入 1_2；
- 一般特定主体进入 1_1，并按基线筛选从 1_2 排除；
- 特定主体名称精确等于 `陕西西咸新区发展集团有限公司` 时，保留基线中的 1_1/1_2 例外及主体限额覆盖顺序；
- 特定实控人保留基线中的 1_1/1_2 路由及实控人限额覆盖顺序；
- 同一主体存在多条基线实际有效约束时无损保留，不新增基线没有的并行约束，也不压缩成单一最高或最低值；
- 同一实控人按基线的日期、业务分类、实控人分组和限额降序规则取最高最终限额，不能使用通用“最严格值”函数替代；
- 担保复用基线的三键关联、穿透分支、总持仓范围和排除条件；
- 关注池在不同生产查询中的真实非对称行为按基线原样保留，不得用理想化统一规则替代。

以上每一项都必须绑定对应生产函数和特征测试；文字说明不能替代可执行金样。

### 3.4 关注池规则

本轮不调整关注池规则，只复现 `579af695...` 的实际行为。

此前讨论的关注池建议暂不进入本轮。若后续实施，必须在本轮投产完成后另建生产规则版本，使每日生产与交易前试算同时变化，并重新生成完整金样。

### 3.5 零值、缺失和不适用

数据质量信息与生产业务结果必须分层，不能用一个枚举混合表达：

- `applicability_status`：`APPLICABLE` / `NOT_APPLICABLE` / `UNDETERMINED`；
- `data_quality_status`：`COMPLETE` / `MISSING_MASTER` / `MISSING_LIMIT` / `MISSING_SNAPSHOT` / `MISSING_INPUT` / `INVALID_INPUT`；
- `calculation_status`：`CALCULATED` / `UNCOMPUTABLE`；
- `production_result`：严格保留 `579af695...` 生成的业务字段和值。

这样可以同时表达“业务维度适用，但主数据缺失”，并避免把数据质量增强误写成生产规则变化。

规则如下：

- 生产业务字段层必须完整复现 `579af695...` 已有的 `fillna(0)`、缺失状态补值和回退行为，不得因本次重构而改变生产金样；
- 数据质量层并行记录真实来源完整性，不覆盖生产业务字段；
- 显式数值 `0` 按基线语义处理；
- 完整持仓事实表中精确无匹配记录，可以在数据质量层标识为真实零持仓；
- 数据集、字段、批次或匹配键不完整时必须记录相应 `MISSING_*`，不得由交易前适配器新增基线之外的 `or 0`、`fillna(0)`、跨类别回退或默认分类；
- 交易前页面能否给出确定建议由数据质量门控决定，但该门控不得反向修改生产金样字段；
- 不适用维度不参加交易前最终可购额度最小值；
- 必需维度数据质量不足时，不得给出确定的交易前最终可购额度。

### 3.6 超限边界和总体状态

- 任一剩余额度 `< 0` 即为超限；
- 剩余额度 `= 0` 不超限，但无新增可购空间；
- 业务判断不得使用 `1e-9` 等容差；
- 展示四舍五入不能改变底层业务状态；
- 生产业务状态严格复现基线；交易前建议状态在其上叠加数据质量门控；
- 已确认超限优先决定交易前总体状态；
- 同时存在不可计算项时必须继续披露其数量和原因；
- 没有确认超限但存在必需不可计算项时，总体为不可计算。

### 3.7 高收益

- 高收益判定调用共同内核；
- 合法空结果表示当前高收益占用为零，不表示数据集缺失；
- 年度全价成本使用预计结算全价金额，包含应计利息、不含手续费，单位万元；
- 高收益拟买全价成本必须大于零；
- 不得用 PR 金额替代全价成本；
- 严格复用上线 `query_high_yield_capital` 的日期和统计范围分组，不另行按自然年重分组；同一基线统计组内的多行全价成本累加；
- 必填全价成本未知时，对应维度不可计算。

不同计量口径必须严格隔离：

- 单券 `raw_pr_remaining_wan` 只在 `PR_WAN` 约束之间取最紧原始剩余，允许为负；
- 单券 `purchasable_pr_cap_wan` 在全部必需 PR 维度可计算时等于 `max(0, raw_pr_remaining_wan)`，否则为空；
- 高收益年度 `full_price_cost_remaining_wan` 单独输出，不与 PR 剩余额度取最小值；
- 篮子分别用拟买 PR 检验 `PR_WAN` 约束，用拟买预计结算全价成本检验 `FULL_PRICE_COST_WAN` 约束；任一计量组超限均可使总体超限；
- 不同 `measure` 禁止交叉聚合、比较或相减；逐维原始剩余值始终保留。

### 3.8 数据时间

- 使用数据库 `current` 指向的最新完整限额快照，不设置 T-1 新鲜度硬门槛；
- 非持仓债使用最新可用 Wind 主数据，不请求与限额快照同日的历史 Wind 数据；
- Wind 为当次请求输入，不落库、不缓存、不向后续查询复用；
- 页面和审计记录必须分别显示限额快照日期和当次 Wind 获取时间/数据日期；
- 数据日期不同本身不导致不可计算，但来源和时间必须可追溯。

## 4. 当前 MVP 数据库上下文契约

本节是当前唯一可实施的数据与运行契约，替代本文件附录 A 中关于“完整事实仓、34 张兼容投影、Wind 落库、独立 TEST 数据库、逐笔审计和全站迁移”的要求。附录 A 仅保留审计追溯价值，不得用于开发、测试、验收或合并。

### 4.1 范围与数据边界

- 每次完整日常运行沿用同一份 Stage0/Stage1/Stage2 生产逻辑，并从本次实际加载的运行期缓存冻结共同内核的 27 个唯一外部输入、业务日期和监管集中度参数；不得在计算后重新打开“当前 Excel”拼装另一版本。
- 同次运行还须从 `Stage1Processor.config` 已解析的路径读取完整 `限额配置_当前.xlsx` 原始字节，作为独立审计附件保存。Stage1 的“系统参数/监管集中度限额”与其余配置 sheet 必须使用同一 `config`；该附件不构成共同内核的第二输入来源。
- 交易前上下文是计算输入，不是展示长表或结果表。既有 `archive_meta`、4 张 Stage0 归档表、12 张展示结果表、展示快照和既有页面完全保持原有读写路径；交易前代码不得读取它们作为共同内核输入。
- 27 个输入为 `STAGE1_REQUIRED_FRAMES ∪ STAGE2_REQUIRED_FRAMES` 的按序去重并集。它们覆盖完整持仓、池、调整、配置、分类、评级、净资产、分母和系统参数；Stage2 的两张 Stage1 交接表由共同内核重算，不另存为外部输入。
- 同时被 Stage1/Stage2 消费的外部输入以 Stage1 在同次运行中实际使用的内存帧为唯一快照来源。现有 Stage2 适配器为保持已上线展示，会从 Stage1 导出的 Excel 重读部分上下文；该重读副本不能替代共同内核输入，也不构成第二套业务口径。
- 已验证的 Excel 往返边界仅为 `债券持仓明细表_信用债` 和 `债券持仓明细表_信用债_合并风险限额相关` 两张 Stage2 原始上下文输出：允许与共同内核同名帧有不超过 `1e-12` 的绝对浮点尾差。该例外只用于验证旧展示读取边界；共同内核的输入、Stage1 全部输出和 Stage2 所有限额计算结果仍逐字段严格相等，业务判断不得使用容差。
- 持仓债必须仅以完整持仓输入判断；持仓但主数据不完整时返回 `MISSING_SNAPSHOT`，不得以 Wind 覆盖冻结快照。非持仓债在当次调用 Wind；Wind 缺少共同内核必需字段时返回不可计算，不得补零、默认分类或解释为不适用。
- `issuer_wind_code_mapping.csv` 是静态解析依赖，不另建历史表，也不在交易前快照重复保存来源清单；冻结金样对其版本的校验保留在独立基线证据中。

### 4.2 三张计算上下文表与一张审计附件表

只允许新增下列 `pretrade_` 前缀表及必要索引：

1. `pretrade_snapshot`：`snapshot_id`、`data_date`、监管集中度参数和 `captured_at`；
2. `pretrade_snapshot_dataset`：每个 `(snapshot_id, dataset_code)` 的 Parquet `schema_json`、`payload_hash` 与单条 `LONGBLOB payload`；
3. `pretrade_snapshot_current`：固定 `pointer_id = 1` 的唯一 `snapshot_id`。
4. `pretrade_config_workbook`：每个 `snapshot_id` 恰有一条的 `限额配置_当前.xlsx` 原始文件名、SHA-256 和完整 `LONGBLOB` 字节。

Parquet 使用固定 Arrow 编码，禁止 pickle 和静默类型降级。快照写入先在内存完成 27 项编码，再在一个事务内插入快照头、全部单载荷和原始工作簿；任一步失败整体回滚。读取时必须校验 27 项精确集合、每项 payload SHA-256、schema 和 Parquet 可读性，并校验工作簿 SHA-256。原件保留全部 16 个 sheet、格式、公式和备注，但不属于 27 项共同内核输入，不参与计算或重放。快照只追加；同日修数生成新的 `snapshot_id`。不保存分块、状态机、用途、来源清单、整体输入 hash、行数、载荷长度或版本字段。

### 4.3 构建、发布与读取

- 正常日常运行只对每个完成的业务数据日构建一次交易前快照。冻结验收和人工数据库验证只写未发布快照；不新增 TEST schema、账号或实例。
- 日常生产编排器先写交易前快照，再执行既有归档；归档成功后，以短事务读回校验 27 项输入和原始配置附件、确认日期一致，并切换唯一 `pretrade_snapshot_current(pointer_id = 1)`。缺少或哈希不符的历史附件不可补造，且该快照不得发布为 current。
- 发布前必须确认 `snapshot.data_date` 等于 `archive_meta.is_current = 1` 的 `data_date`。交易前读取端也必须执行相同检查；两者不一致时只返回“数据同步中”，不能使用新旧批次混算。
- 日常数据使用最新完整的已有业务数据，不以 T-1/T-2 新鲜度作为阻断归档条件；实际 `data_date` 必须可解析并展示。缺少必需输入、日期不一致、输入集合不完整、Parquet 往返失败或哈希不符仍必须失败。
- 在线交易前服务只通过唯一 current 指针读取 27 项数据库输入；它不得读取 Excel、ACCDB、`data/current`、公盘、本地业务配置或展示快照。Wind 是唯一按请求进入内存的外部输入。

### 4.4 MVP 明确不做的事项

本阶段不实现事实表、34 张兼容投影、旧页面迁移、`ArchiveDB` 改造、除当次 `限额配置_当前.xlsx` 审计附件之外的原始文件入库、对象存储、Wind 表/缓存、逐笔审计、发布审计流水、并发发布/回滚体系、独立 TEST 账号或全站 UI 改版。它们如有需要，必须在本 MVP 零差异验收后另立规格。

## 附录 A（SUPERSEDED）：原全量闭包架构草案

本附录记录已否决的全量架构，以便审计追溯。它不覆盖本文件第 1-4 节，也不产生任何实施、验收或数据库要求。

### A.1 共同边界

持仓适配器和 Wind 适配器只能输出同一份“规范原始债券主数据记录”，不得在适配器内完成池表关联、限额分类或适用性判断。

两类来源都可以提供的外部原始事实包括：债券余额、外部评级字段、发行人、原始实控人、原始担保人及其代码、省份、行业等。Wind 字段是否能解释为生产字段必须由显式映射和字段级来源证明；不得把普通主体评级自动当作中债隐含评级。

以下内部信息始终从同一个 `snapshot_id` 读取，并由共同内核处理：

- 债券池和主体池成员关系；
- 内部中债隐含评级参考表或调整表；
- 内部担保准入名单、担保限额关系；
- 发行人类型调整和实控人调整；
- 高风险名单、地域及行业参考；
- 净资产及其他分母；
- 全部限额配置和系统参数。

持仓债若复用已计算的派生上下文，只能把它作为共同函数的不可变缓存；必须证明从规范原始输入重新执行共同内核得到完全一致的结果。缓存不得成为独立业务路径。

### A.2 持仓和主数据存在性

数据库必须分别记录：

- `is_held`：完整持仓事实中是否有持仓；
- `master_present`：规范债券主数据是否存在；
- `master_complete`：规范债券主数据是否满足共同内核所需字段；
- `position_dataset_complete`：持仓事实数据集是否完整。

判定顺序固定为：

1. 持仓且主数据完整：从数据库取得规范原始记录，进入共同内核；
2. 持仓但主数据不完整：标记 `MISSING_SNAPSHOT`，禁止用 Wind 覆盖冻结主数据；
3. 非持仓且数据库已有满足当前 Wind 有效策略的最新兼容 `READY` 规范主数据：直接复用该固定版本；
4. 非持仓但没有满足有效策略的完整版本：由独立 Wind 采集服务获取最新数据、不可变落库并完成规范化后再计算；
5. 持仓数据集不完整：不能确认是否持仓，标记 `MISSING_SNAPSHOT`，禁止调用 Wind 假定其为非持仓。

是否持仓只能由完整持仓事实表判定，不能从 1_1、1_2 或其他筛选后的展示/信用债结果表判定。

### A.3 Wind 规范化

1. Wind 只补充外部原始主数据，不提供内部池状态、内部调整表结果或限额配置；
2. Wind 原始担保人关系与内部担保准入/限额关系分别保存，只有共同内核可以按基线规则关联二者；
3. 原始响应与规范化记录分别、不可变地落库；
4. 映射器不得把主体评级静默当作中债隐含评级，不得自行推断未被基线支持的发行人类型或内部担保准入；
5. 映射完成后与数据库持仓主数据进入同一个业务内核；
6. 映射所需字段缺失时记录字段级来源和稳定数据质量原因码。

### A.4 “全部计算数据读库”的运行边界

- 批量归档进程可以读取 Excel、ACCDB 和公盘；
- Wind 采集服务可以访问 Wind，并使用独立受限写账号写入 Wind 表；
- 在线单券和篮子计算进程不得读取 Excel、ACCDB、`data/current`、公盘、本地 JSON 或 YAML 业务配置，也不得直接访问 Wind；
- 在线计算所用持仓、主数据、配置、参考数据、分母及 Wind 规范记录必须通过显式 `snapshot_id` 从数据库读取；
- 页面只提交交易请求并读取结果，不持有快照或 Wind 采集写权限；
- 验收时必须实际撤销在线计算进程对业务目录和外部网络的访问，不能只依赖代码约定。

### A.5 数据库契约

现有 34 张归档表在过渡期保留为兼容投影，但不得继续按 `data_date` 独立覆盖和发布：

- 每张兼容表增加并强制使用 `snapshot_id`；
- 它们与新事实表在同一批 `LOADING` 快照中生成和验证；
- 既有页面的数据加载层与新页面一样，先解析一次统一 `limit_snapshot_current`，随后全部按同一个 `snapshot_id` 查询；
- current 发布或回退时，全系统页面仅随同一个指针变化，不另外复制、覆盖或切换旧表；
- 第一次切换前必须生成同时包含 34 张兼容投影和新数据闭包的完整 `READY` 快照；禁止部分页面提前切换；
- 历史按 `data_date` 管理的旧数据可以只读保留，但不得参与新 current，也不得补入共同内核。

因此，共同内核和既有页面都不能从旧表按 `data_date` 拼接输入；所有计算及展示数据必须属于同一个不可变 `snapshot_id`。

#### A.5.1 跨表约束

- 所有快照子表包含 `snapshot_id CHAR(36) NOT NULL`，外键指向 `limit_snapshot(snapshot_id)`，并使用 `ON DELETE RESTRICT`；
- 全部业务表使用显式 DDL 和 InnoDB；
- 金额使用 `DECIMAL(28,8)` 并明确单位，比例使用 `DECIMAL(18,10)`，日期使用 `DATE`，时间使用 UTC `DATETIME(6)`；
- 每张表明确主键、业务唯一键、空值规则、单位和必要索引；
- `source_row_id` 由 `dataset_id + sheet/table + 稳定源行键` 生成，并保存源文件、sheet、原始行号及业务键；不得使用重排后 DataFrame index；
- 业务数据只允许在快照为 `LOADING` 时写入；快照进入 `READY` 后，应用账号不得更新或删除其任何业务行；
- 合法状态迁移仅为 `LOADING → VALIDATED → READY`、`LOADING/VALIDATED → FAILED`；`READY` 和 `FAILED` 都是终态；
- “不再是 current”不修改快照状态，通过 current 切换历史表达，避免与不可变性冲突；
- 在线应用只读取其明确兼容的 `schema_version + rule_version + engine_version`；版本不兼容必须失败关闭。

#### A.5.2 `limit_snapshot`、current 与发布审计

`limit_snapshot` 至少包含：

- `snapshot_id` UUID 主键；
- `environment`：`TEST` / `PROD`；
- `data_date`、`archive_date`；
- `status`：`LOADING` / `VALIDATED` / `READY` / `FAILED`；
- `code_commit`、`rule_version`、`engine_version`、`schema_version`、`mapping_version`；
- `dependency_lock_hash`、`source_manifest_hash`、`timezone`；
- `created_at`、`validated_at`、`ready_at`、`failed_at`；
- `parent_snapshot_id`、失败原因和创建身份。

同一数据日重跑必须创建新 `snapshot_id`，不得覆盖旧批次。

`limit_snapshot_current` 至少包含：

- `environment` 主键；
- `snapshot_id`；
- `previous_snapshot_id`；
- 单调递增 `switch_seq`；
- `switched_by`、`switch_reason`、`switched_at`；
- 用于乐观并发控制的 `row_version`。

另建追加式 `limit_snapshot_publish_audit`，记录每次发布、回退、失败尝试、旧/新指针和操作身份。

current 切换算法固定为：

1. 发布者取得环境级 advisory lock，或对 current 行执行 `SELECT ... FOR UPDATE`；
2. 验证目标快照属于同一环境、状态为 `READY` 且版本与应用兼容；
3. 在一个短事务内更新 current 并追加发布审计；
4. 提交后释放锁；
5. 回滚只把指针切回以前兼容的 `READY` 快照，不删除或修改新快照；
6. Schema 迁移必须向后兼容，否则不得声称仅靠指针即可回滚。

#### A.5.3 原始数据闭包

`limit_snapshot_dataset` 逐逻辑数据集记录：

- `dataset_code`、来源文件、sheet/table 和读取用途；
- 权威业务日期字段、最小/最大日期；
- 行数、列清单、schema hash 和 content hash；
- 完整性状态；
- 是否允许合法空表；
- 完整数据集无匹配时是否可解释为零。

主键为 `(snapshot_id, dataset_code)`。

为保证可精确重放，另建不可变的 `limit_snapshot_dataset_column` 和 `limit_snapshot_dataset_row`：

- 列表保存原列名、顺序、逻辑类型、空值语义和单位；
- 行表保存稳定 `source_row_id`、原始顺序、规范序列化 payload 和行哈希；
- 所有 payload 由同一版本序列化器生成，能够恢复生产代码实际读取的数据类型和空值。

快照必须覆盖共同内核使用的全部输入，而不仅是展示结果，至少包括：

- `data_source_0123` 中实际消费的全部文件和 sheet；
- 完整穿透持仓和核算系统持仓事实；
- 规范债券主数据；
- 净资产及监管、地域、高风险等全部比例分母；
- 债券池、主体池、担保关系和 Stage0 派生输入；
- 德勤评级、中债隐含评级、发行人类型调整、实控人调整；
- 金融工具池、穿透高收益、高风险行业/省份、地域及标准日期参考；
- 本次运行内存中实际使用的全部限额配置和系统参数；
- Stage2 所需历史持仓和高收益全价成本事实；
- Stage1/Stage2 生产规范中间记录、当前占用和最终约束。

配置和参考数据必须从本次生产运行实际加载的内存对象归档，不能在生产计算完成后重新打开“当前 Excel”采集另一版本。

#### A.5.4 共同内核类型化事实表

原始数据闭包用于审计和重放；在线共同内核读取同一 `snapshot_id` 下的类型化事实表：

1. `bond_master_fact`
   - 主键 `(snapshot_id, canonical_bond_id)`；
   - 标准债券代码、ISIN、外部发行人/实控人/担保人原始字段；
   - `master_present`、`master_complete`、字段级来源及质量状态；
   - 不保存由限额分类器自行推断的第二套类别。
2. `position_fact`
   - 主键 `(snapshot_id, source_row_id)`；
   - 完整持仓范围、账户、日期、PR、全价成本和源行血缘；
   - 包含判断 `is_held` 及 Stage2/高收益所需的所有事实，不能只保存信用债筛选子集。
3. `net_asset_fact`
   - 主键 `(snapshot_id, data_date, scope_key)`；
   - 保存净资产值、单位、来源和完整性。
4. `production_reference_fact` 与 `production_config_fact`
   - 按 `dataset_code + stable_row_key` 保存共同内核实际使用的类型化配置和参考数据；
   - 所有行强制绑定 `snapshot_id`。
5. `production_position_context`
   - 主键 `(snapshot_id, source_row_id)`；
   - 保存 Stage1 共同内核生成的完整合并风险上下文、1_1/1_2 路由、排除原因和生产业务字段；
   - 不得从最终 1_1/1_2 展示表拼回。
6. `production_exposure`
   - 主键 `(snapshot_id, dimension_code, business_class, scope_key, measure)`；
   - 保存共同内核已经算定的当前占用，用于对账和性能缓存，不能替代原始事实重新定义规则。
7. `production_constraint`
   - 主键 `(snapshot_id, constraint_id)`；
   - `constraint_id` 由规则来源、业务分类、维度、主体、范围和基线约束类别稳定生成；
   - 保存限额来源、覆盖关系、当前占用、剩余、生产状态及三层质量状态；
   - 无损保留基线已有的主体多约束、实控人最终取值、西咸及特定覆盖、担保和其他排除原因。

#### A.5.5 Wind 不可变采集和规范化

Wind 原始响应与规范化记录必须分表、版本化：

1. `wind_request`
   - 不可变 `wind_request_id`；
   - 标准债券代码、请求参数、供应商、请求时间、调用身份；
   - 幂等键覆盖债券代码、字段集合、请求参数和有效窗口。
2. `wind_raw_response`
   - 不可变 `wind_master_id`；
   - 原始响应、响应哈希、请求/返回时间、Wind 数据日期；
   - `LOADING` / `READY` / `FAILED`、错误码和字段完整性；
   - 重试创建新版本，不覆盖旧响应。
3. `wind_normalized_master`
   - 主键 `(wind_master_id, snapshot_id, mapping_version)`；
   - 记录规范字段、字段级来源、`code_commit`、`rule_version` 和质量状态；
   - 明确该规范记录使用哪个快照的内部参考数据；
   - 计算端只能读取 `READY` 原始响应对应的完整规范记录。

计算开始时一次性选定每只债券最新的兼容 `READY` 版本，并固定到本次 `pretrade_run`；计算期间不得自动切换。

Wind 有效策略本身版本化为 `wind_validity_policy_id`。首版策略为：仅当最新兼容 `READY` 版本在当前 Asia/Shanghai 自然日获取、请求字段集合完整且 `mapping_version` 兼容时才复用；否则由采集服务重新请求并创建新版本。该策略不要求 Wind 数据日期与限额快照日期相同。

#### A.5.6 交易前试算审计模型

采用追加式模型：

- `pretrade_run`：运行头、`snapshot_id`、代码/引擎/规则/映射版本、原始输入哈希、规范输入哈希、结果哈希、调用身份、时间和 `PENDING/READY/FAILED`；
- `pretrade_run_line`：逐行原始交易输入、规范账户、PR、全价成本、输入状态；
- `pretrade_run_master_link`：每行关联的 `canonical_bond_id` 或 `wind_master_id`；一揽子可关联多个 Wind 版本；
- `pretrade_run_dimension`：逐维范围、当前占用、拟买增量、限额、剩余、生产状态、三层质量状态和原因码。

任何历史试算必须能够仅凭上述 ID 和版本重放。Wind 采集写账号、试算审计写账号和快照发布账号相互分离、最小授权；页面读账号不具备这些写权限。

#### A.5.7 事务和故障约束

1. Schema 迁移与每日业务事务分开；
2. 一个批次先写 `LOADING`，再写全部数据闭包和类型化事实；
3. 完成日期、必需列、允许为空、行数、哈希、版本兼容和生产差分检查后转为 `VALIDATED`；
4. 只有全部验证通过才转为 `READY`；
5. 读端在一个只读可重复读事务中取得一次 `snapshot_id` 并加载全部上下文；
6. 禁止按 `data_date` 从不同批次逐表拼接；
7. 故障测试必须注入：任意表写失败、验证失败、切换前崩溃、current 事务失败、并发发布者和回退后旧版本读取；
8. 任一失败不得修改上一版 current，也不得留下可被在线应用读取的半成品。

| 统计报表底稿1_债券.xlsx 的实际消费 sheet | 按基线读取后，权威 `日期` 必须解析为目标日；无法解析或出现冲突立即失败 |
| 统计报表底稿2_债券SPPI.xlsx 的实际消费 sheet | 按基线读取后，权威 `日期` 必须解析为目标日；无法解析或出现冲突立即失败 |
| 债券持仓表.xlsx | 可以包含历史日期，但必须包含目标日；共同内核严格按 Stage1 信用债业务日关联筛选 |
| 净资产.xlsx | 必须能按基线日历展开逻辑得到目标日净资产 |
| 标准日期表.xlsx | 必须包含目标日及基线所需交易日映射 |
| 限额配置及静态参考文件 | 无快照业务日期要求，以 manifest 哈希和本次运行实际加载版本绑定 |

`snapshot.data_date` 只能由上述规则和显式 `expected_data_date=2026-07-10` 共同验证产生，不得来自文件修改时间、归档时间或某一张最终结果表的最大日期。

### 5.3 路径和环境隔离

- 显式设置 `LIMIT_MONITOR_PROFILE=local`；
- 使用 `realpath` 校验每一个输入，解析后的绝对路径必须位于冻结根目录内；符号链接逃逸立即失败；
- 禁止共享盘与本地样本之间任何静默回退；
- 基线运行和重构运行分别使用唯一、不可复用的输出目录；
- 输出根目录必须执行 `realpath` 校验，只允许位于显式 TEST 输出白名单根目录内；
- 拒绝任何符号链接逃逸；
- 输出路径等于或位于 `data/current`、生产归档目录或公盘目录时立即退出；
- 基线或重构目标目录已经存在时拒绝复用，不能自动清空后覆盖；
- 测试运行账号在文件权限层面不得写入现有 `data/current` 和生产归档目录；
- 所有验收查询显式指定 `DEV snapshot_id`，禁止依赖 `PROD` current。

### 5.4 `DEV` 逻辑隔离

- 开发、自动化验收和人工验证使用既有阿里云数据库的 `pretrade_` 表，但构建命令固定写 `usage=DEV`；不创建独立 TEST schema、账号或实例。
- `DEV` 构建命令拒绝 `PROD`、发布和既有归档写入参数；它不得调用 `ArchiveDB.write_batch()` 或修改 `archive_meta`、既有 16 张归档表、展示快照。
- `PROD` current 只能由生产日常编排器在既有归档成功且两个 `data_date` 一致后切换；`DEV` current 不受 `archive_meta` 日期守卫影响。
- 基线、`DEV` 快照和重放证据均记录唯一 `snapshot_id`、manifest 和输出哈希。

在隔离输出、路径校验、27 输入契约和 `DEV` 指针保护全部落地以前，不允许直接运行生产日常编排器进行数据库验收。

## 6. 验收门槛

### 6.1 生产内核重构零差异

基线必须由 GitHub 提交 `579af695...` 在独立输出目录、使用冻结 manifest 生成，并永久记录代码、依赖、输入和每个输出文件的内容哈希。使用相同输入对重构前后的 Stage0/Stage1/Stage2 比较：

- 输出数据集集合；
- 行数和稳定业务键；
- 适用范围；
- 1_1/1_2 路由；
- 当前占用；
- 限额类别、限额来源和限额值；
- 剩余额度；
- 超限状态；
- 基线已经输出的缺失和不适用业务字段。

本轮所有生产业务差异必须为零，不设置批准例外。比较协议必须固定：

- 每张表的稳定业务键和排序；
- 列顺序、逻辑数据类型和空值规范；
- 金额和比例的规范序列化精度；
- 行级、字段级和数据集级哈希；
- 仅由二进制浮点序列化造成的差异单独报告，不自动通过；
- 任何可能改变 `<0`、分组、匹配、适用性或限额选择的差异一律失败；
- 差分产物、审核结论和批准身份持久化归档。

新增三层数据质量字段单独验收，不能与生产业务字段混在“零差异”比较中，也不能覆盖基线结果。

### 6.2 数据库回放

- 用 `data_source_0123` 的冻结输入构建正式数据库中的 `DEV` 快照；快照恰含 27 个输入、参数和来源元数据。
- 仅从指定 `DEV snapshot_id` 读回 27 个 dataset 并重建 `ProductionKernelInput`；该验收读取路径禁用文件 I/O 与网络 I/O。
- 读回后运行共同内核，Stage1 35 张和 Stage2 的全部限额计算输出与冻结金样逐表、逐行、逐字段零差异。Stage2 的两张命名 Excel 往返原始上下文表按第 4.1 节验证：共同内核值须与 Stage1 同名输出严格相等，且与旧 Stage2 展示副本的绝对浮点尾差不得超过 `1e-12`。
- Parquet 列顺序、逻辑类型、日期、Decimal/数值、空值、行数、payload hash 和总输入 hash 必须通过；合法空表、显式零和缺失输入必须能区分。
- 同一 `data_date` 两次构建必须产生不同 `snapshot_id`；写块、hash、读回或反序列化失败时，事务回滚且旧 `DEV`/`PROD` current 不变。

### 6.3 单券与篮子（后续服务阶段）

- 单行篮子与单券结果一致；
- 零增量还原交易前状态；
- 拆单、合单和行顺序不改变结果；
- 同一债券、主体、实控人、担保人、地域、行业及高收益年度范围正确合并；
- 篮子结果必须与“将交易增量追加到规范输入后调用同一业务内核”的结果一致；
- 一行主数据失败不污染无关风险范围，但不得把失败行从其可能影响的共享范围中静默剔除；相关共享范围及总体状态必须受数据质量门控；
- 共享分母所需数据缺失时，相关范围明确不可计算。

### 6.4 Wind（后续服务阶段）

- 自动化回归使用固定的 Wind 响应夹具，夹具只在测试内存中经同一规范化器进入共同内核；不得写数据库、缓存或本地业务文件。
- 真实 Wind 只验证连通性和字段完整性，不以实时返回作为可重复期望值，也不持久化请求或响应。
- Wind 映射后的规范记录必须通过与持仓债相同的业务内核测试；必需字段缺失必须返回不可计算及原因。

### 6.5 数据库故障

- 同日重跑生成新快照；
- 中途失败不切 current；
- 读取端只看到完整 `READY` 快照；缺 dataset、非连续 chunk、hash 不符或反序列化失败必须关闭读取；
- 注入任一 dataset 写入、chunk 写入、hash 校验或读回失败时，旧指针保留；
- `DEV` snapshot 不得发布到 `PROD`；`PROD` 发布的 `data_date` 与 `archive_meta` current 不一致时必须拒绝；
- 本 MVP 不实现并发发布、发布审计流水、物理账号隔离或指针回滚体系。

### 6.6 前端回归（后续页面阶段）

- 只修改单券和篮子两个页面；
- 其他页面的导航、数据、筛选、导出和展示结果不得变化；
- UI 验收必须在业务与数据库验收通过后进行。

## 7. 实施顺序

1. 冻结 GitHub 上线提交和本规格；
2. 建立隔离输出、冻结输入清单和正式数据库中的 `DEV` 上下文；
3. 对上线 Stage0/Stage1/Stage2 生成特征金样；
4. 抽离文件 I/O 与纯业务内核，确保生产结果零差异；
5. 建立 27 输入的 `pretrade_` 不可变快照并从数据库重放生产上下文；
6. 建立同进程日常编排、既有归档后的日期守卫发布；
7. 实现持仓债交易增量和非持仓债 on-the-fly Wind 规范化；
8. 实现单券与篮子薄应用层；
9. 完成全量差分、故障和前端回归；
10. 最后决定合并、正式归档和生产切换。

## 8. 明确禁止事项

- 禁止从最终展示表反推完整生产规则；
- 禁止在交易前模块复制 Stage1/Stage2 公式；
- 禁止使用当前配置替代快照实际配置；
- 禁止跨限额类别兜底；
- 禁止适配器或交易前模块新增基线之外的缺失默认为零；基线已有默认行为必须保留在生产业务字段，并由并行数据质量字段披露；
- 禁止按 `data_date` 拼接不同运行批次；
- 禁止在线计算进程读取文件、公盘、本地业务配置、展示快照或旧展示表；非持仓债仅可通过当次 on-the-fly Wind 适配器进入内存；
- 禁止从旧 16 张归档表按日期补入共同内核所需配置、参考或分母；
- 禁止测试写入 `PROD` 指针、`archive_meta`、既有 16 张归档表或覆盖 `data/current`；`DEV` 仅可写 `pretrade_` 表；
- 禁止在业务差分未通过前合并前端分支；
- 禁止仅凭页面看起来合理或单次完整归档成功判断业务正确。

## 9. 完成定义

只有同时满足以下条件，两个新增功能才可以进入生产：

1. 每日生产和交易前试算调用同一业务内核；
2. `data_source_0123` 生产重构业务差异为零，不存在本轮批准例外；
3. 数据库能够独立恢复共同内核的 27 个外部输入、参数和计算上下文；
4. 持仓债全量逐维对账通过；
5. 非持仓债 on-the-fly Wind 映射和共同内核回归通过；
6. 篮子不变量和直接重算对账通过；
7. 数据库事务、重跑、并发和回滚测试通过；
8. 其他页面零回归；
9. 在线计算在无业务文件访问、无共享盘条件下通过数据库上下文验收；Wind 仅作为非持仓债的当次内存输入；
10. 输入、快照、规则和试算结果均可审计重放；
11. 业务负责人确认最终差分报告。
